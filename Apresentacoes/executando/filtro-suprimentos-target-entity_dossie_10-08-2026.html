O filtro de Suprimento que casa Contrato

Um filtro cuja condição diz "Suprimento" na tela casa contatos que não têm suprimento nenhum — porque o motor não obedece a condição que você vê, e sim um segundo campo (target_entity) que a interface nunca preenche. Diagnóstico do executivo ao técnico: o que quebra, por que o re-save não corrige, e onde está a raiz.

O sintoma

Aparece no filtro, mas a carteira mostra "nenhum suprimento"

O filtro "Suprimentos teste" lista contatos como Josiane Costa de Oliveira e Rodrigo Bergmann. Ao abrir a carteira de cada um → aba Suprimentos, vem "Nenhum suprimento encontrado". A primeira intuição é que a carteira está com bug. É o contrário: a carteira está certa — eles têm zero suprimento — e é o filtro que casa quem não deveria.

Em uma frase

O filtro retorna 5.716 contatos, mas só 2.216 têm suprimento de verdade. Os ~3.500 restantes casam por causa do contrato legado, não do suprimento.

A causa · os dois campos

Dois campos dizem "suprimento vs contrato". A UI seta o errado.

Sua pergunta estava certa: são dois campos distintos que, na API, codificam a mesma decisão. A tela preenche o visível; o motor obedece o invisível. Quando discordam, vence o invisível — e ele nunca foi preenchido.

o que a UI seta ✓

conditions[].table

Campo por condição. É o dropdown "Suprimento" que você vê na regra. Define de qual tabela vem a coluna daquela linha.

table: "supplies"
field: "total_value"

Persiste corretamente no re-save — por isso a tela continua mostrando "Suprimento".

o motor usa →
o que o motor obedece ✗

filter_definitions.target_entity

Campo do filtro inteiro (escopo-raiz). Decide contra qual partição entity_kind da base o filtro roda. É coluna própria, fora das condições.

target_entity: "contracts"
deveria ser "supplies"

A UI não tem controle para ele, e nada o deriva da condição.

redundância por design

Para um filtro de suprimento, os dois deveriam dizer "supply". Eles são redundantes na dimensão suprimento×contrato — mas ninguém os reconcilia. A base vw_titles_live é um UNION de duas partições (entity_kind='contract' = mundo legado; entity_kind='supply' = suprimentos), e só o target_entity escolhe a partição.

O motor · backend

O compilador está correto — só obedeceu um valor errado

O compilador compile_filter_to_sql_v2 deriva o recorte do target_entity, não da condição. Com target_entity='contracts', ele injeta entity_kind='contract' e ainda mapeia a coluna de suprimento para a de contrato. O SQL que sai é este:

-- Filtro salvo: condição supplies.total_value > 1, target_entity = 'contracts' -- SQL efetivamente gerado: (contract_original_value)::NUMERIC > 1 AND entity_kind = 'contract' -- ← recorte vindo do target_entity -- Traduzindo: "todo contato com CONTRATO legado de valor > 1" — quase a base inteira. -- Nunca olha entity_kind = 'supply'.
-- O que DEVERIA sair (se target_entity = 'supplies'): (contract_original_value)::NUMERIC > 1 AND entity_kind = 'supply' -- ← recorta suprimento → 2.216 contatos (bate com a realidade)

Consumidores já leem o campo certo

A contagem do card (evaluate_filters_batch) e a lista do drawer (get_filter_contacts_paginated) — verificados no banco vivo — leem target_entity e o repassam ao compilador. O motor faria a coisa certa se o valor salvo estivesse certo. Não há bug de runtime.

A raiz · frontend

Por que o target_entity nunca vira "supplies"

O caminho de salvar o filtro (escrita direta na tabela, sem edge function) tem quatro lacunas que, somadas, garantem que todo filtro de suprimento nasça e permaneça como "contracts".

◆ iaf

A UI não expõe o campo

  • 1O modal "Editar Filtro" só tem Nome, Cor, Descrição, Ícone, "Escopo" (que é usage_scope, outra coisa) e as condições.
  • 2Não há seletor de "entidade-alvo". O schema do formulário nem inclui target_entity.
  • 3O dropdown "Suprimento" só grava rule.table na condição — nunca toca o filtro.
◆ iaf

Nada deriva, nada atualiza

  • 4Nenhum código lê a condição e conclui target_entity='supplies'.
  • 5CREATE: default fixo target_entity: data.target_entity || "contracts", e o valor da UI é sempre undefined → nasce "contracts".
  • 6UPDATE: o payload nem inclui o campo → o Postgres mantém o valor antigo. É por isso que seu re-save não corrigiu.
// useFilters.ts — CREATE nasce 'contracts' (data.target_entity é sempre undefined vindo da UI) transformCreate: (data) => ({ name: data.name, conditions: data.conditions, target_entity: data.target_entity || "contracts", }) // filter-builder/index.tsx — UPDATE monta o payload SEM target_entity → coluna intocada const filterData = { name, description, conditions, color, icon }; // ← sem target_entity await updateFilter.mutateAsync({ ...filterData, id: filter.id });

O banco não segura

Coluna target_entity é VARCHAR(50) DEFAULT 'contracts', sem CHECK e sem trigger que a reconcilie com as condições. A única edge function que escreve filtro (ai-proposal-executor) também omite o campo. O IAF-4795 entregou o lado da leitura; o lado da escrita no front nunca foi fechado.

Veredito

O erro é no frontend. O backend está correto.

Frontend — defeituoso

Não seta nem deriva target_entity; no UPDATE nem manda o campo. Raiz do erro.

Backend — correto

Deriva entity_kind corretamente do valor recebido. Fez a conta certa com o dado errado.

Banco — frágil

Default 'contracts', sem CHECK/trigger. Backstop, não origem — mas um endurecimento desejável.

Correção recomendada

Fechar a escrita no front — e endurecer o banco

1

Se alguma condição usa supplies/supply_titles → target_entity='supplies'. Calcular no submit.
2
Mandar no CREATE e no UPDATE
Incluir o campo no payload e adicionar o transformUpdate (hoje inexistente) para ele entrar no .update().
3
Trava no banco
Trigger/CHECK que reconcilie target_entity com as condições — pega qualquer writer desatualizado. Via CI/CD.

decisão de produto

O recorte-raiz é único (entity_kind é ou/ou), então filtro misto contrato+suprimento não é representável hoje. A UI deveria impedir misturar as duas famílias na mesma definição, ou exigir escolha explícita da raiz.

Risco secundário a validar

No ramo de suprimento, contract_original_value não é igual a supplies.total_value linha-a-linha (parece agregado por parcela). Para o limiar > 1 é inócuo, mas um filtro de suprimento por faixa de valor pode errar mesmo com o target_entity certo. Validar a projeção da view antes de confiar.

Fechada a escrita no front + a trava no banco, filtros de Suprimento passam a funcionar por construção — a condição que você vê e o motor voltam a concordar.
Em resumo
◆ iaf

A tela mostra "Suprimento". O motor obedece "Contrato".

Dois campos codificam a mesma decisão suprimento×contrato: a table da condição (que a UI seta) e o target_entity do filtro (que o motor usa). A interface nunca preenche o segundo nem o deriva do primeiro, e o UPDATE nem o envia — por isso o re-save não corrige. O bug é de frontend; o backend está correto; o banco não tem trava que reconcilie.
