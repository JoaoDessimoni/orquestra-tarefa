O que é · como funciona · por quê

Um relógio sobre cada CCB não cedida

Quando uma CCB é assinada, começa a contar o prazo para cedê-la ao FIDC. Passar do prazo significa perder a janela de cessão. A rotina varre diariamente a base, encontra as CCBs que estão entrando na zona de risco e avisa quem precisa agir — com listas prontas e valores somados.

O gatilho: o vencimento

O “vencimento” da CCB é a DATA_LIMITE_DESEMBOLSO (equivalente a celcoin…disbursement_date). É a âncora do cálculo — não confundir com o cronograma de parcelas.

Dias restantes = vencimento − hoje (fuso America/Sao_Paulo).

O universo

CCBs assinadas (proposal com signed_at), com negociação ativa, das duas operações, ainda não cedidas ao FIDC e não canceladas.

Também exclui as que já foram efetivamente desembolsadas (DATA_DESEMBOLSO_EFETIVO IS NULL).

O universo Celcoin monitorado tem ~974 CCBs (gold_ccb_celcoin); o funil de regras afunila para as ~77 em alerta hoje.

As duas operações

Ideal — negociação na Plataforma Blips (produto a119c37e…).

Outros Originadores — Portal de Negócios / Finza Start (demais produtos). Cada faixa gera dois XLSX: um por operação.

▲ Contexto: por que existe este projeto

A demanda nasceu de um script legado em Google Apps Script (script-ccb.js) que puxava CCBs da API da Flow para uma planilha e mandava e-mails de status. O objetivo foi recriar e elevar essa ideia em n8n — com dados direto do BigQuery, segmentação por faixa/operação, WhatsApp oficial (HSM) e log auditável de envios.

O alerta é escalonado em três faixas de dias restantes. A diretoria, por exemplo, só entra na faixa crítica. As barras abaixo mostram a distribuição real do painel em 07/07/2026.

⚠ Lacuna conhecida das faixas — validar com a área

As faixas cobrem 10–15, 7–9 e ≤5 dias. Sobram lacunas no dia 6 (nenhuma faixa captura) e a faixa crítica virou “≤5” — ou seja, captura 5, 4, 3… e também dias negativos (atrasadas). Isso foi uma decisão de implementação para não deixar CCB sem alerta abaixo de 5 dias, mas precisa de confirmação: (a) o dia 6 deve entrar em alguma faixa? (b) atrasadas devem continuar sendo alertadas?

Arquitetura de dados · BigQuery

De onde vem cada informação

A spec original apontava um bloqueio: “finza-prod.proposal não está no BigQuery”. Na investigação, descobriu-se que tudo já estava no BQ — o que destravou construir a rotina inteira em SQL, sem tocar no MongoDB.

✔ Descoberta que destravou tudo: a chave da Kanastra

A spec dizia que contract_number = document_number — mas isso dava 0 de 964 matches. A chave real é gold.ID_SEQUENCIAL = kanastra…document_number. Validado por correlação: dos “Cedidos”, 705/741 estão na Kanastra; dos “Não Cedidos”, 0/92. Por isso a exclusão de “já cedida” usa ID_SEQUENCIAL NOT IN (SELECT document_number …).

✔ Cancelamento Ideal: a spec também errou

A spec afirmava que o contract_number da Plataforma não casa com o do Finza Start. Falso: 916 de 927 CCBs Ideal batem em PLATAFORMA.negotiation.contract_number = gold.NUMERO_CONTRATO. Usa-se só phase.status (limpo). customer_withdrawal foi descartado por ser ruidoso (92 deals ativos tinham a flag = true).

◆ A validar com a área: “Endosso Assinado” ≠ cessão concluída

126 CCBs com status “Endosso Assinado” não aparecem na Kanastra — logo, seriam alertadas. Se “endosso assinado” já significar cessão fechada, elas deveriam ser excluídas. Ponto aberto.

As queries · explicadas

Todo o negócio mora no SQL

Três queries BigQuery sustentam a rotina. A principal é a “Buscar CCBs em alerta” — ela concentra 100% das regras de negócio (universo, exclusões, faixas, operação).

Buscar CCBs em alerta · node BigQuery retryOnFail ×3
WITH prop AS (
  SELECT contract_number, signed_at, proposal_status FROM (
    SELECT JSON_VALUE(data,'$.contract_number') AS contract_number,
      SAFE_CAST(JSON_VALUE(data,'$.document_signature_info.signed_at') AS TIMESTAMP) AS signed_at,
      JSON_VALUE(data,'$.status') AS proposal_status,
      ROW_NUMBER() OVER (PARTITION BY JSON_VALUE(data,'$.contract_number') ORDER BY _airbyte_extracted_at DESC) rn
    FROM `finza-prod-481500.bronze.proposal`
    WHERE JSON_VALUE(data,'$.contract_number') IS NOT NULL
  ) WHERE rn = 1
),
cedidas AS (
  SELECT DISTINCT CAST(document_number AS INT64) seq
  FROM `blips-bigdata.kanastra.repository_finza` WHERE document_number IS NOT NULL
),
canc_blips AS (
  SELECT DISTINCT contract_number FROM `blips-bigdata.PLATAFORMA.negotiation`
  WHERE phase.status IN ('CANCELLED','CANCELLATION_REQUESTED') AND contract_number IS NOT NULL
),
base AS (
  SELECT g.*,
    DATE_DIFF(g.DATA_LIMITE_DESEMBOLSO, CURRENT_DATE('America/Sao_Paulo'), DAY) AS dias
  FROM `finza-prod-481500.gold_flow_finance.gold_ccb_celcoin` g
)
SELECT
  b.NUMERO_CONTRATO, b.ID_SEQUENCIAL, b.NOME_CLIENTE, b.CNPJ_CLIENTE,
  b.VALOR_REQUISITADO, b.NOME_EQUIPAMENTO,
  DATE(p.signed_at) AS DATA_ASSINATURA,
  b.DATA_LIMITE_DESEMBOLSO AS DATA_VENCIMENTO,
  b.dias AS DIAS_RESTANTES,
  CASE WHEN b.ID_PRODUTO='a119c37e-db4b-4462-bb60-a2a32fccc025' THEN 'IDEAL' ELSE 'OUTROS' END AS OPERACAO,
  CASE
    WHEN b.dias BETWEEN 10 AND 15 THEN '15_10'
    WHEN b.dias BETWEEN 7 AND 9 THEN '9_7'
    WHEN b.dias <= 5 THEN '5'
  END AS FAIXA
FROM base b
LEFT JOIN prop p ON b.NUMERO_CONTRATO = p.contract_number
WHERE p.signed_at IS NOT NULL
  AND b.ID_SEQUENCIAL NOT IN (SELECT seq FROM cedidas)
  AND b.STATUS_ORIGINAL <> 'CANCELED'
  AND COALESCE(p.proposal_status,'') <> 'CANCELLED'
  AND b.NUMERO_CONTRATO NOT IN (SELECT contract_number FROM canc_blips)
  AND b.DATA_DESEMBOLSO_EFETIVO IS NULL
  AND (
    b.dias BETWEEN 10 AND 15
    OR b.dias BETWEEN 7 AND 9
    OR b.dias <= 5
  )
ORDER BY OPERACAO, FAIXA, DIAS_RESTANTES

As 4 CTEs

  • prop — lê o JSON cru do bronze.proposal, extrai signed_at e status, e deduplica por contrato (ROW_NUMBER pela carga mais recente). Evita o fan-out do join.
  • cedidas — todos os document_number da Kanastra = CCBs já cedidas.
  • canc_blips — contratos cancelados na Plataforma (operação Ideal).
  • base — o gold_ccb_celcoin + cálculo de dias.

As exclusões (o WHERE)

  • Só assinadas: signed_at IS NOT NULL.
  • Fora as já cedidas (Kanastra) e as canceladas (Ideal + Outros).
  • Fora as já desembolsadas: DATA_DESEMBOLSO_EFETIVO IS NULL.
  • Só quem cai em alguma faixa.

⚠ Duas armadilhas de SQL tratadas aqui

(1) NOT IN com NULL zera o resultado — por isso todo subquery de exclusão tem IS NOT NULL. (2) o join com bronze.proposal causaria fan-out (linhas duplicadas) — resolvido deduplicando por contrato via ROW_NUMBER antes do join.

Query simples, mas central para a parametrização sem front-end: lê apenas os destinatários ativos. O modelo é por pessoa — cada linha é um responsável, com arrays de faixas, canais e operacoes que ele acompanha. Roda executeOnce porque a lista de destinatários é a mesma para todas as CCBs.

Buscar data referencia · node BigQuery executeOnce · ancestral
WITH datas AS (
  SELECT
    (SELECT DATE(MAX(HORARIO_ULTIMA_CARGA)) FROM `finza-prod-481500.gold_flow_finance.gold_ccb_celcoin`) AS gold_dt,
    (SELECT MAX(SAFE.PARSE_DATE('%Y-%m-%d', reference_dt)) FROM `blips-bigdata.kanastra.repository_finza`) AS kanastra_dt
),
lm AS (
  SELECT
    (SELECT TIMESTAMP_MILLIS(last_modified_time) FROM `finza-prod-481500.gold_flow_finance.__TABLES__` WHERE table_id='gold_ccb_celcoin') AS gold_lm,
    (SELECT TIMESTAMP_MILLIS(last_modified_time) FROM `blips-bigdata.kanastra.__TABLES__` WHERE table_id='repository_finza') AS kanastra_lm,
    (SELECT TIMESTAMP_MILLIS(last_modified_time) FROM `blips-bigdata.PLATAFORMA.__TABLES__` WHERE table_id='negotiation') AS plataforma_lm
)
SELECT
  COALESCE(kanastra_dt, gold_dt) AS DATA_REFERENCIA,
  FORMAT_DATE('%d/%m/%Y', COALESCE(kanastra_dt, gold_dt)) AS DATA_REFERENCIA_BR,
  FORMAT_DATE('%d/%m/%Y', gold_dt) AS GOLD_CARGA_BR,
  FORMAT_DATE('%d/%m/%Y', kanastra_dt) AS KANASTRA_REF_BR,
  FORMAT_TIMESTAMP('%d/%m/%Y %H:%M', gold_lm, 'America/Sao_Paulo') AS GOLD_LM_BR,
  FORMAT_TIMESTAMP('%d/%m/%Y %H:%M', kanastra_lm, 'America/Sao_Paulo') AS KANASTRA_LM_BR,
  FORMAT_TIMESTAMP('%d/%m/%Y %H:%M', plataforma_lm, 'America/Sao_Paulo') AS PLATAFORMA_LM_BR,
  IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(gold_lm,'America/Sao_Paulo'), DAY),999) AS gold_lm_dias,
  IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(kanastra_lm,'America/Sao_Paulo'), DAY),999) AS kanastra_lm_dias,
  IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(plataforma_lm,'America/Sao_Paulo'), DAY),999) AS plataforma_lm_dias,
  GREATEST(
    IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(gold_lm,'America/Sao_Paulo'), DAY),999),
    IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(kanastra_lm,'America/Sao_Paulo'), DAY),999),
    IFNULL(DATE_DIFF(CURRENT_DATE('America/Sao_Paulo'), DATE(plataforma_lm,'America/Sao_Paulo'), DAY),999)
  ) AS MAX_DIAS_DESATUALIZADO
FROM datas, lm

Faz duas coisas. (1) Data de referência exibida = a reference_dt do estoque da Kanastra (exatamente a fonte que o docx §9 indica; o gold_dt entra só como guarda contra nulo, via COALESCE). A Kanastra atrasa ~4 dias, então é ela que define “de quando” é o dado; vai para e-mail, WhatsApp e log. (2) Sinal de freshness do gate = o maior atraso de last_modified (quando a TABELA foi escrita, via __TABLES__) entre gold, Kanastra e Plataforma → MAX_DIAS_DESATUALIZADO, comparado a 2 dias no nó “Fontes atualizadas?”. Atenção: reference_dt (data do conteúdo) ≠ last_modified (escrita da tabela) — o gate mede a saúde do pipeline, não a data do dado.

⚙ Detalhe de arquitetura: por que é um nó ancestral, não paralelo

Vários nós fazem $('Buscar data referencia'). Se esse nó fosse um ramo paralelo do gatilho, ele rodaria fora de ordem e quebraria com “node hasn't been executed”. A solução foi encadeá-lo como ancestral: Gatilho → Buscar data referencia → Buscar CCBs → …

Modelo por pessoa (uma linha por responsável), diferente do schema coluna-a-coluna que a spec sugeria. Cada pessoa declara em quais faixas, canais e operações quer ser avisada. Para a diretoria receber só na crítica, basta faixas = ['5'].

➕ Cadastrar sem escrever SQL — raia de formulário

Há uma raia própria pra popular a tabela sem tocar no BigQuery: Form Trigger cadastrar-destinatario-ccb → Montar INSERT destinatário (Code) → Inserir destinatário (BigQuery). O formulário usa checkboxes pra Faixas/Canais/Operações e radio pra Ativo — opções fixas, sem digitação livre, então é impossível gravar um valor que o alerta não reconheça.

Por que a higienização importa: o cruzamento no Estruturar envios por faixa é exato e case-sensitive — operacoes precisa ser exatamente 'IDEAL'/'OUTROS', canais 'email'/'whatsapp'. Um cadastro com "Ideal" (minúsculo) ou "email. whatsapp" (ponto em vez de vírgula) não bate em nada e a pessoa não recebe. Por isso o Montar INSERT destinatário blinda a entrada:

  • split por vírgula / espaço / ponto / ; / |;
  • canais → minúsculo (+ apelidos wpp/zap→whatsapp); operacoes → MAIÚSCULO; faixas normaliza traço→_;
  • valida contra os conjuntos permitidos e descarta valores inválidos;
  • telefone → só dígitos, prefixa 55, checa 12–13 dígitos; e-mail via regex;
  • se faltar algo essencial, rejeita com mensagem em vez de gravar lixo.

Correções pontuais numa linha já existente saem por outra raia manual — 🔧 Atualizar contato (manual) → Atualizar contato (UPDATE) (BigQuery com a credencial de escrita) — porque a credencial BigQuery do assistente é somente leitura.

Como difere da query de alerta (#1)

Mesma “espinha” de CTEs (prop · cedidas · canc_blips · base), mas o WHERE é o oposto no espírito: em vez de excluir pagas/cedidas/canceladas, ela inclui todas numa janela de vencimento de −30 a +15 dias e devolve as colunas de status. É isso que permite registrar quando cada CCB foi paga/cedida. Hoje: 314 CCBs na janela (222 pagas · 15 canceladas · 77 em alerta). O nó Formatar acompanhamento deriva a coluna Situação e a flag Em alerta?, e o resultado vai para a aba Acompanhamento via appendOrUpdate (sem clear).

Lógica dos nós Code (JavaScript)

Como o SQL vira faixas, listas e mensagens

Depois do BigQuery, nós Code em JS montam a estrutura de envio, formatam a planilha e preparam cada canal. O coração é o nó “Estruturar envios por faixa”.

🧩 Estruturar envios por faixa

Emite um item por contato (não mais por faixa). Para cada destinatário, filtra as CCBs do escopo dele (FAIXA ∈ faixas e OPERACAO ∈ operacoes) e monta o breakdown faixa × operação incluindo os zeros ("nenhuma"), as listas ccbs_ideal/ccbs_outros, o total, as faixa_linhas (1 linha por faixa) e num_faixas. Contato sem nenhuma CCB no escopo é pulado.

📋 Formatar p/ planilha · Só Ideal / Só Outros

Traduz cada CCB para colunas legíveis (rótulos em português, datas em dd/mm/aaaa, faixa “15–10 / 9–7 / ≤5”) e carimba “Última atualização”. Depois um filtro por _op separa nas abas Ideal e Outros Originadores.

✉ Preparar e-mail · Contatos c/ e-mail · Loop

Filtra só contatos com e-mail, itera um contato por vez (Loop), gera os XLSX Ideal/Outros do escopo dele, e monta o HTML com uma tabela Faixa × Operação (com "nenhuma" nos zeros) + total. Anexa só os arquivos com linha (a propriedade de anexo do Gmail é dinâmica: Object.keys($binary)).

💬 Preparar WhatsApp

Gera uma mensagem por contato: normaliza o número, monta uma linha por faixa (*≤5 dias* — Ideal: N CCBs (R$…); Outros: nenhuma) e envia {numero, nome, faixa1, faixa2, faixa3, num_faixas, total, data_ref, token}. O num_faixas é o que o Hyperflow usa para escolher o template certo (1/2/3 faixas).

Estruturar envios por faixa · trecho — 1 item por contato, escopo faixa × operação Code node
const has = (arr, v) => Array.isArray(arr) && arr.includes(v);

for (const d of dest) {                       // um item POR CONTATO
  const faixas = ['5','9_7','15_10'].filter(fx => has(d.faixas, fx));   // mais urgente 1º
  const ops    = ['IDEAL','OUTROS'].filter(op => has(d.operacoes, op));
  if (!faixas.length || !ops.length) continue;

  const mine = alertas.filter(r => faixas.includes(r.FAIXA) && ops.includes(r.OPERACAO));

  // 1 linha por faixa, com as operações do contato (inclui "nenhuma"):
  const faixa_linhas = faixas.map(fx => {
    const perOp = ops.map(op => {
      const rows = mine.filter(r => r.FAIXA===fx && r.OPERACAO===op);
      return rows.length ? `${oL[op]}: ${rows.length} CCBs (${fmt(soma(rows))})`
                         : `${oL[op]}: nenhuma`;
    });
    return `*${fL[fx]} dias* — ${perOp.join('; ')}`;
  });
  // → { nome, email, numero, faixa_linhas, ccbs_ideal, ccbs_outros,
  //     total_qtd, total_valor, breakdown, faixas_texto }
}

A planilha · painel + log

Cinco abas, uma fonte de verdade operacional

A automação escreve numa planilha Google (1ZCy…gPX7E) que serve tanto de painel quanto de log auditável. Cada aba tem um papel.

🔄 Painel (Ideal / Outros): limpa e reescreve

A cada execução, os nós Limpar Ideal / Limpar Outros (Google Sheets clear · executeOnce) zeram a aba, e então Planilha: Ideal / Outros (append) reescrevem cabeçalho e linhas do zero.

Assim o painel é sempre o retrato fiel do dia: colunas na ordem certa (incluindo as de status) e zero CCB já resolvida sobrando. Como a query traz o universo completo do dia, limpar-e-reescrever é seguro.

➕ Log Envios: só adiciona

Operação append puro — nunca atualiza. Cada disparo (e-mail ou WhatsApp) gera uma linha nova, com status real e link para a execução. É o histórico de auditoria, então acumular linhas aqui é o comportamento desejado.

✔ Onde mora cada coisa: alerta fiel ao docx, status no board

As abas Ideal e Outros (e os XLSX do e-mail) trazem exatamente as colunas da demanda (nº, cliente/CNPJ, valor, assinatura, vencimento, dias, faixa, originador) — nada de status, para ficar fiel ao docx. Como voltaram às colunas originais, o cabeçalho estilizado que já existe continua válido; o clear do n8n apaga só os valores (não a formatação nem o congelamento), então o cabeçalho estilizado/frozen se mantém a cada run.

Já todo o status por CCB — inclusive quando foi paga/cedida — vive na nova aba Acompanhamento (ver aba abaixo).

Decisão: sem retry no envio, log tolerante a falha

Os nós de envio usam onError: continueRegularOutput e não têm retry — de propósito, para nunca duplicar mensagem. Se falhar, a linha do log registra a falha e a execução segue. O retry existe só nos nós de leitura (BigQuery) e de escrita em planilha (Sheets).

Por que é separado do alerta

O alerta, por definição, exclui pagas/cedidas — então “paga” nunca apareceria lá. O board usa uma query mais ampla que as inclui e, por não limpar (appendOrUpdate), mantém a trilha de cada CCB.

Setup único: criar e estilizar o cabeçalho

O n8n escreve valores, não formata células. Então, uma vez só: crie a aba Acompanhamento, deixe o 1º run preencher as colunas (ou cole os cabeçalhos na ordem) e aplique a mesma formatação da aba Ideal (negrito/cor + congelar linha 1). Como o appendOrUpdate nunca reescreve o cabeçalho, a formatação persiste nas próximas execuções.

Governança de dados · §9 da spec

Nunca alertar sobre base defasada

Data de referência = reference_dt da Kanastra

Fiel ao docx §9, a data de referência é a reference_dt do estoque da Kanastra (gold_dt só como guarda de nulo). Como a Kanastra atualiza em D+~4, é ela que define “de quando” é o dado. Essa data aparece no e-mail, no WhatsApp e no log, para todo mundo saber a referência.

Robustez operacional

Fuso fixo America/Sao_Paulo; BigQuery/Sheets com retryOnFail; batching do WhatsApp 1 msg / 1,5s + timeout 20s; nós de visão (“Entradas”, “Resumo da execução”) para inspecionar cada run direto na aba Executions.

✓ Gate de freshness — passo a passo

1. Mede o atraso. O nó Buscar data referencia lê o last_modified_time (via __TABLES__) de gold_ccb_celcoin, kanastra.repository_finza e PLATAFORMA.negotiation, calcula há quantos dias cada uma foi escrita e guarda o maior atraso → MAX_DIAS_DESATUALIZADO.
2. Decide. O nó IF Fontes atualizadas? testa MAX_DIAS_DESATUALIZADO <= 2:

  • Fresco (≤ 2d): segue para Buscar CCBs em alerta → dispara e-mail/WhatsApp normalmente.
  • Defasado (> 2d): NÃO dispara os alertas; desvia para Avisar Dados (base defasada), que manda um e-mail ao time de Dados (hoje marcos.oliveira@finza.com.br).

O "2 dias" é default nosso, não do docx. A §9 só diz "além do limite aceitável" (sem número) e que as fontes "são atualizadas diariamente" — escolhemos 2 (folga de fim de semana). É parametrizável no nó IF (a confirmar — Q3). E usa last_modified (a tabela foi escrita? = saúde do pipeline), não o reference_dt (data do conteúdo, que atrasa por natureza).
